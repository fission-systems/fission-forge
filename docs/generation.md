# Bounded generation from Forge checkpoints

`forge generate` loads model tensors from a training checkpoint and performs
full-prefix greedy decoding. There is no KV cache, sampling, beam search,
repair loop, or source-reference lookup. EOS and the 256 byte tokens are legal
completion tokens; PAD/BOS/SEP are masked. Ties choose the lowest legal token ID.
The token budget is 1..4,096; context limits stop generation without truncating
the input. Every step recomputes the whole prefix, so this is a correctness-first
inference path, not a serving-throughput benchmark.

```sh
cargo run --locked -p fission-forge -- generate \
  --checkpoint outputs/checkpoint \
  --prompt outputs/compiled-input/prompt.txt \
  --representation pcode-plus-ssa-v1 \
  --max-new-tokens 256 --output outputs/generation
```

Use a fresh output path. `completion.bin` preserves exact generated bytes;
`completion.txt` is written only when those bytes are valid UTF-8. `report.json`
records the checkpoint/state/prompt hashes, model configuration, input lane,
backend, token IDs, byte values, and stop reason (`eos`, `max_new_tokens`, or
`context_limit`). EOS is a model stop signal, not proof that the text is valid C.
No invalid bytes or partial outputs are silently rewritten.

New checkpoint schema 3 records training input lanes. Generation rejects a lane
not listed in that checkpoint before loading weights. Older schema 1/2 checkpoints
can be loaded, but missing lane metadata remains unrecorded; the DecBench adapter
accepts schemas 3 and 4. Training resume accepts schema 2 with its effective-batch hash
and schema 1 for legacy assembly; new smoke saves upgrade to schema 3.
The separate [corpus trainer](corpus-training.md) writes schema 4 with sampler
state and a weights-file digest. Generation checks this digest and uses the
recorded query-tile size. Corpus training resumes through `train-corpus`.

The loader reads the Safetensors file into host memory and transfers only model
tensors to the requested device. AdamW payload bytes are not used for inference.
CPU generation is exercised here. CUDA/Metal use the CLI backend flags and need
separate generation validation; previous CUDA training probes are not generation
throughput evidence.

## Recorded connection probe

The 61,888-parameter model was trained for 160 updates on exactly one owned,
compiled callee example with a 446-byte v1 prompt. CPU greedy decoding reproduced
its 51-byte C label and EOS. This is deliberate memorization to validate the
checkpoint-to-generation path. The unit suite also trains a short assembly/C
software fixture and checks exact generated C and EOS. Neither is held-out
accuracy or evidence of general decompilation quality.

For the recorded IR probe, extract only the small callee row from the fixture set:

```sh
mkdir -p outputs
python3 - <<'PY'
import json
from pathlib import Path
rows = [json.loads(line) for line in Path('fixtures/pcode-cfg/pairs.jsonl').read_text().splitlines()]
row = next(row for row in rows if row['id'] == 'forge_callee')
Path('outputs/callee.jsonl').write_text(json.dumps(row, separators=(',', ':')) + '\n')
PY
cargo run --locked -p fission-forge -- train-smoke \
  --config configs/model/tiny-ir.json --dataset outputs/callee.jsonl \
  --learning-rate 0.005 --steps 160 --output outputs/checkpoint
cargo run --locked -p fission-forge -- pcode-compile \
  --raw fixtures/pcode-cfg/forge_callee.raw.json \
  --profile configs/lifter/fission-x86_64.json \
  --representation pcode-plus-ssa-v1 --output outputs/compiled-input
```

Then run `generate` above. Training loss is recorded separately from generation
success. Reports and the generated fixture C are in [the evidence record](../evidence/2026-10-20-cfg-generation/README.md).
